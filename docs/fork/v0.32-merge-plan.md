# Merge plan: upstream v0.32.0 into dp-stable

Spike output for PAIINFRA-227. The merge itself is PAIINFRA-228. This plan is the input for that
merge. Review it before the merge starts.

- From: `dp-stable` at `7088896f` (upstream v0.29.3 plus the fork patches)
- To: upstream tag `v0.32.0` (`ecb9a8d84`), 130 upstream commits
- Trial merge: 36 files in conflict, 2 of them modify/delete. Three more files merge without
  conflict markers but do not compile (see [Silent breaks](#silent-breaks)).

## Summary

1. **vMCP sessions.** In v0.32.0 the tool and resource calls no longer use the per-session backend
   connections. Each backend call makes a new client, initializes it, calls, and closes it
   (`pkg/vmcp/client/client.go`, `httpBackendClient.CallTool`). Any pod can restore a session from
   Redis (#5650). Thus most fork session patches protect a code path that does not exist any more.
   The plan drops owner forwarding, claim, handover and backend reconnect, and re-ports the
   behaviour that is still necessary onto the new `Serve` path.
2. **Auth.** Take upstream. #5651 returns 401 with `WWW-Authenticate` when an upstream token refresh
   fails. That replaces the fork's upstream-token status map (`c2cb472a2`). Add one small fork fix
   for a case that upstream does not cover (see [Auth](#auth)).
3. **CRDs.** The upstream CRD changes are additive. The only removed field is the fork's own Redis
   `address` alias (item 4), which no live object sets. The merged CRDs are safe to serve under the
   v0.29.3 fork operator. They must roll out before any v0.32 operator: the v0.32 operator does not
   start without the new `MCPAuthzConfig` CRD.
4. **Drop the Redis `address` alias in this merge**, as FORK.md planned. Checked on 2026-10-12 (see
   [Redis `address` alias](#redis-address-alias)): all values use `addr`, no live object sets
   `address`, and no cluster runs the `f904` operator any more.

## vMCP sessions and HA

### How v0.32.0 serves a session

| Request | On the pod that created the session | On another pod |
|---|---|---|
| `tools/list` | Tools from `core.ListTools` with the live identity | `lazyInjectSessionTools` fills the tools from the core. Works. |
| `tools/call` | `enforceSessionBinding`, then `core.CallTool` | Lazy inject, then restore from Redis (opens all stored backends, up to 15 s), then the binding check. Works. The first call on that pod is slower. |
| `resources/*` | Works | No lazy-inject hook. Empty or not found. **Gap.** |
| `GET` (listen stream) | Works | mcp-go registers the session again, and the registration hook can write a new binding. **Suspected re-bind, confirm with a test.** |
| `DELETE` | Deletes the Redis key | The creating pod keeps its cached session with open backend connections until eviction. **Leak.** |
| Pod that created the session dies | – | Nothing to hand over. Any pod restores from Redis. In-flight calls are lost, the same as today. |

No DocPlanner VirtualMCPServer uses elicitation, sampling or composite tools (checked in
`platform-apps/charts/toolhive-config*` and `docplanner-helm/stable/toolhive-config`). So no
client reply must reach the pod that sent the request, and owner routing has no remaining job.

### GET re-registration

Confirmed on 2026-10-12 with `TestCrossPodSessionRebind` (`pkg/vmcp/server/serve_crosspod_rebind_test.go`):
two `Serve` servers share one session store, alice initializes on pod A, then GET and POST
`tools/call` go to pod B as alice and as another user, eve.

- **Mechanism.** mcp-go v0.55.0 `handleGet` (`server/streamable_http.go:703-746`) does not validate
  the session id. When the session is not in the pod's memory it calls `RegisterSession`, which
  fires `OnRegisterSession` → `handleSessionRegistrationImpl` (`server.go:1077`) →
  `CreateSession` (`server.go:1105`). `CreateSession` (`session_manager.go:281`) checks only that the
  record exists and is not terminated. It builds a new session with the caller's identity and
  overwrites the stored binding (`session_manager.go:369`).
- **Different identity.** Any authenticated user of the same vMCP who knows a session id takes the
  session over with one GET on a pod that does not have it in memory. The owner is then rejected
  and the session is terminated.
- **Same identity.** Every GET or SSE reconnect on another pod opens new backend connections and
  overwrites the stored backend session ids.
- **POST `tools/call` is safe.** mcp-go validates the id, the pod restores the session and
  `enforceSessionBinding` rejects a different caller.

| Case | v0.32.0 | v0.39.0 | v0.40.0 |
|---|---|---|---|
| GET on pod B, same identity | Fail (new session made) | Fail | Pass |
| GET on pod B, different identity | Fail (binding moves to eve) | Fail | Pass |
| POST `tools/call` on pod B, both identities | Pass | Pass | Pass |

- **dp-stable today is not exposed while the owner pod is alive.** The fork forwards every GET and
  DELETE to the owner pod (`shouldForwardToSessionOwner`). D1 removes that forwarding, so v0.32
  needs the guard.
- **Upstream.** There is no targeted fix. The bug goes away in v0.40.0 as a side effect of #5729
  (mcp-go replaced by toolhive-core `mcpcompat`, whose rehydration does not fire
  `OnRegisterSession`). v0.33.0 to v0.39.0 are affected, so the guard stays until the fork reaches
  v0.40. `CreateSession` has no "already bound" check even on upstream main. This is a security bug
  in released versions: report it to Stacklok privately (GitHub security advisory), not as a
  public issue.
- **Open on v0.40+.** A GET from another user still opens a listen stream on the rehydrated session.
  Whether that user can receive the owner's server-to-client messages is not tested.

### Risk that stays after the merge

- **More backend sessions.** Session create still opens one connection to each backend
  (`sessionmanager.CreateSession`) and keeps it for the life of the session, but calls do not use
  it. Each `tools/call` adds one more initialize, call and DELETE. In prod, about 2k client sessions
  a day become about 20k backend sessions a day (from the `logs-toolhive.audit` counts of the week
  to 2026-10-12). If DELETE does not remove the proxyrunner session keys, Dragonfly holds about 10
  times more keys for 24 h. Prod Dragonfly ran out of memory at 512Mi on 2026-09-15. Measure on stg.
- **Cross-pod restore cost.** The first `tools/call` on another pod opens all backends of the
  session. Measure the latency on stg.
- **Refresh timing (accepted, D4).** The caching aggregator keeps results for 30 s. With the 15 s
  debounce and the 60 s cooldown, clients can see an old tool set for up to about 2 minutes after a
  backend change. Both values are constants in `pkg/vmcp/server/refresh_scheduler.go` and apply to
  every vMCP. If a cluster ever needs other values, the smallest change is an env var read at start,
  set on the `vmcp` container through the VirtualMCPServer `spec.podTemplateSpec`. That needs no CRD
  change.

### Backend MCPs and the new call model

Checked on 2026-10-12 for every MCP in `platform-apps/charts/toolhive-config*` and the base chart.

- **No MCP needs state between calls.** Most servers already run in stateless HTTP mode (FastMCP
  `stateless_http`, kubernetes-mcp `--stateless`, mcp-for-argocd `--stateless`, aws-mcp and
  falcon-mcp stateless env, elastic-mcp `NeverSessionManager`). Follow-up ids (memory-mcp
  `search_id`, cilium-flows query id, amplitude-experiment approvals) are stored in Redis or Athena,
  so they work on any pod.
- **stdio servers** (sentry, pagerduty, phrase, vanta, supernova): one process serves all sessions.
  More `initialize` calls only. Check memory on stg.
- **mongodb-atlas-mcp** keeps one server instance for each `Mcp-Session-Id` (120 s idle timeout on
  i0). Each call now makes a new instance. Measure memory on stg. Lower `MDB_MCP_IDLE_TIMEOUT_MS` if
  DELETE does not reach it.
- **mcp-proxy backends** (datadog, backstage, sre-incidents, datasage) forward the session id, so
  each call opens a new upstream session. Check rate limits on stg.
- **rabbitmq `initialize_connection*`**: not a session problem. The tool changes the connection of
  the whole backend process, for every user, on one replica. 0 calls in 30 days. Hide it with a
  `toolsFilter` in the base chart `rabbitmq` preset. That is a separate base chart change, not part
  of this merge.

## Order of work

The merge commit resolves every conflict to upstream's behaviour and compiles. The fork behaviour
then comes back in separate commits on the same branch, so that each one can be reviewed and later
replayed. The CRDs are final at the merge commit, so the CRDs PR (PAIINFRA-230) can pin it.

1. Merge commit: resolve as in this plan, fix the silent breaks, drop the Redis `address` alias,
   regenerate CRDs, mocks and docs. `task build` passes with no fork session behaviour.
2. Small keeps: Redis username, `WithSessionIdleTTL`, write timeout, init timeout,
   `sessionTTLFromConfig`, detached registration context.
3. Per-workload request timeouts on the backend client.
4. `RestorableCache` sweep and local-first `Terminate`.
5. Wait for registration in `enforceSessionBinding`.
6. Health-probe short-circuit.
7. Resource lazy inject and the "clear and notify" refresh.
8. Guard against GET re-registration (required, D5). Add `TestCrossPodSessionRebind` to the fork in
   the same commit. Drop the guard when the fork reaches v0.40 or later, if the test still passes
   without it.
9. Required upstream provider check (auth fix).
10. Tests: delete the owner-forwarding and recovery tests, rewrite the rehydration and registration
    tests for the `Serve` path, add tests for steps 5 to 9. Then `task lint-fix` and `task test`.
11. FORK.md: drop the rows for owner URL, refresh, `CreatorIdentity` and the `address` alias, and
    add the new rows.

## Check on stg (PAIINFRA-231)

### Functional checks

- Delete a hub pod during an active session. The session continues on another pod, with no forced
  re-auth.
- No "session not found", "caller authorization failed" or stale-backend errors after the cutover.
- A `tools/call` sent right after `initialize` succeeds.
- `resources/list` works on a pod that did not create the session.
- After a backend goes unhealthy and healthy again, Cursor and Codex clients see the new tool set.
- Calls longer than 30 s work, and `timeouts.perWorkload` is applied.
- The hub vMCP Deployment generation stays stable (#5617).
- **Pod hardening (D7).** After the cutover every MCPServer, proxy and vMCP pod on stg is `Running`
  and `Ready` again under `seccompProfile: RuntimeDefault` and `capabilities.drop: [ALL]`. No pod
  is in `CrashLoopBackOff` or `CreateContainerError`. List any image that fails in PAIINFRA-229.

### Load scenarios (D2)

Stg has almost no users (2 to 7 a day, peak 35 calls a minute, against 93 to 137 users and peak
321 calls a minute on prod). So every scenario uses a synthetic client: a Python `mcp`
streamable-http client with a stg Cognito automation client, against `hub-agents`. Run each one on
v0.29.3 first to get a baseline, then on the v0.32 merge.
